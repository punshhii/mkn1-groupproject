# ПС-6 Целостность (fw-integrityd)

- **Язык:** Python 3
- **Пользователь ОС:** `fw-integrityd`
- **Требования:** FR-45 – FR-50
- **Команда:** Митяев, Цыбукова (вместе с ПС-5: Волнухина, Карцев)
- **Сокет:** `/run/fw/integrityd.sock` (с. 31: 0660, владелец `fw-integrityd`, группа `fw-mgmt`; `protocol.serve` пока ставит 0600)

---

## 1. Назначение и реализуемые требования

Подсистема **ПС-6 Целостность** контролирует целостность исполняемых и конфигурационных файлов ПО МЭ, переводит МЭ в режим аварийной поддержки при нарушении и восстанавливает файлы из резервных копий.

### Реализуемые требования спецификации (`report/report.pdf`, с. 16):
- **FR-45 (ТЗ 6.1):** Контролируются исполняемые файлы и библиотеки ПО МЭ, файлы конфигурации, политики доступа и учётных записей, скрипты запуска.
- **FR-46 (ТЗ 6.1):** Контроль выполняется автоматически с периодом из таблицы 3 (60 с, допустимо 10–3600 с, с. 8), при запуске МЭ и по запросу администратора (`E42`). Целостность определяется сравнением хэша SHA-256 с эталоном.
- **FR-47:** Изменения, выполненные администратором штатными командами, обновляют эталонное значение. Файл эталонов защищён HMAC-SHA-256 с ключом, доступным только ПС-6; несовпадение HMAC считается нарушением целостности.
- **FR-48 (ТЗ 6.2):** При нарушении целостности хотя бы одного файла: заблокировать весь обрабатываемый трафик, очистить таблицу состояний, перейти в режим аварийной поддержки, зарегистрировать `E40` и вывести `M08`. Управляющий доступ (консоль, SSH, HTTPS) сохраняется.
- **FR-49 (ТЗ 6.2):** В режиме аварийной поддержки доступны только просмотр, проверка целостности и восстановление файлов; остальные команды отклоняются с `M10`. Перед восстановлением копия сверяется с эталоном; копия с несовпадающей контрольной суммой не используется.
- **FR-50:** Эталонные контрольные суммы и резервные копии формируются до установки ПО — при сборке установочных пакетов в доверенной среде. Резервные копии хранятся в каталоге пользователя `fw-integrityd` и обновляются при каждом штатном изменении контролируемых файлов.

### Связанные требования других разделов:
- **FR-04 (с. 12):** Если сохранённых файлов конфигурации и политики нет (первый запуск), загружаются значения по умолчанию. ПС-1 стартует заблокированной, политика загружается только после успешной проверки ПС-6.
- **FR-28 (с. 14):** Событие регистрируется независимо от результата; для неуспешной операции добавляется причина.
- **FR-41a (с. 15):** После успешной записи `config save` ПС-6 обновляет эталонные хэши.

## 2. Структура подсистемы и модули

```text
integrityd/
├── README.md                  # Данное описание подсистемы и интерфейсов
└── fw_integrityd/
    ├── __init__.py            # Пакет fw_integrityd
    ├── __main__.py            # Конфигурация, сервер Unix-сокета, диспетчер команд integrity.*
    ├── hasher.py              # SHA-256 файлов, файл эталонов под HMAC-SHA-256
    ├── checker.py             # Проверка при запуске, по таймеру и по запросу; обновление эталона
    ├── emergency.py           # Режим аварийной поддержки, события в ПС-2
    ├── restore.py             # Восстановление файлов из резервных копий
    └── mkbaseline.py          # Эталоны, резервные копии и ключ HMAC при сборке пакета (FR-50)
```

### Модули

#### `hasher.py`
- `BaselineError` — файл эталонов недоступен, повреждён или HMAC не совпал (FR-47).
- `sha256_file(path)` — хэш SHA-256 файла (FR-46).
- `load_key(path)` — чтение ключа HMAC (`/etc/fw/hmac.key`).
- `load_baseline(path, key)` — чтение файла эталонов (путь файла и хэш SHA-256) с проверкой HMAC.
- `save_baseline(path, files, key)` — запись файла эталонов с новым HMAC (через временный файл, 0600).

Формат `baseline.json` (в спецификации задано только «путь файла и хэш SHA-256, файл защищён HMAC», с. 30). HMAC-SHA-256 считается от `json.dumps(files, sort_keys=True, ensure_ascii=False, separators=(",", ":"))` в UTF-8:

```json
{
  "files": {"/etc/fw/config.json": "<sha256 hex>", "/usr/lib/fw/bin/fw-filter": "<sha256 hex>"},
  "hmac": "<hmac-sha256 hex>"
}
```

#### `checker.py`
- **Константы:** `SAVED_FILES` (`/etc/fw/config.json`, `/etc/fw/policy.json` — файлы `config save`), `ACCOUNTS_FILE` (`/etc/fw/accounts.json`), `UPDATED_FILES` (какие файлы штатно меняет каждый источник).
- `compare(files, baseline)` — сравнение хэшей контролируемых файлов с эталоном; статусы `ok`, `mismatch` (хэш не совпал или нет эталона), `missing` (файла нет или он не читается), `not_saved` (см. ниже).
- `violations(result)` — нарушения из результата проверки: `{"baseline_error", "files"}` только с нарушенными файлами (поле `details` события `E40`, `E42`).
- `Checker.check()` — проверка: HMAC файла эталонов, затем SHA-256 каждого файла. Возвращает `{"last_check_ts", "ok", "baseline_error", "files": [{"path", "status"}]}`: поля `last_check_ts` и `files` как в заглушке ПС-6 стенда CLI, `ok` и `baseline_error` добавлены нами. Если файл эталонов или ключ недоступны или HMAC не совпал — `baseline_error` с причиной, `files` пуст, `ok = false`. Статус `not_saved` не считается нарушением. Реакция подключается через `on_result`: он вызывается под блокировкой и не должен блокировать, иначе проверка, начатая до восстановления, включила бы режим уже после выхода из него.
- `Checker.last_result()` — результат последней проверки (`integrity.status`). Читается без блокировки: не ждёт идущую проверку и не запускает её.
- `Checker.update_baseline(src)` — обновление эталона и резервных копий после штатного изменения (FR-47, FR-50). Пересчитываются только файлы источника: `cli` и `web` — `SAVED_FILES`, `authd` — `ACCOUNTS_FILE`, и только если файл входит в `integrityd.files`. При первом `config save` запись в эталоне создаётся. Нарушенный HMAC не переподписывается (`BaselineError`), недоступный файл не исключается из эталона (`OSError`): в обоих случаях эталон не меняется.
- `Checker.restore_files(target)` — восстановление файла или всех нарушенных файлов (`all`) с повторной проверкой. Возвращает `(result, errors)`, в `errors` — `[{"path", "reason"}]` по файлам, которые не восстановлены. Плохая копия одного файла не мешает восстановить остальные.
- `Checker.start_periodic()` / `Checker.stop()` — периодическая проверка с периодом `check_period_sec`. Первая проверка таймера идёт через период: при запуске её уже выполнила служба. Сбой одной проверки контроль не прекращает.

**Первый запуск (FR-04).** Файлы `SAVED_FILES` могут ещё не существовать: тогда работают значения по умолчанию. Различить первый запуск и удаление файла позволяет эталон: его запись появляется при первом `config save`, а без ключа HMAC её не подделать. Детали реализации в спецификации не заданы.

| Файл | Запись в эталоне | Статус | Нарушение |
|---|---|---|---|
| нет | нет | `not_saved` | нет |
| есть, хэш совпал | есть | `ok` | нет |
| есть, хэш другой | есть | `mismatch` | да |
| нет | есть | `missing` | да |
| есть | нет | `mismatch` | да |
| не читается | любая | `missing` | да |

Статус `not_saved` возможен только у `SAVED_FILES`: любой другой файл без файла и без эталона получает `missing`.

#### `emergency.py`
- **Константы:** `EVENT_QUEUE_MAX = 1000`, `EVENT_RETRY_SEC = 5` (очередь событий при недоступной ПС-2, с. 32), `DELIVERY_RETRY_SEC = 5` (допущение), `RUN_DIR`, `CLIENTS = ("cli", "web")`.
- `_Delivery` — доставка команд одной подсистеме: свой поток на получателя (ПС-1, ПС-3, ПС-4), повторы до подтверждения, новая задача заменяет недоставленную.
- `Emergency.start()` / `Emergency.stop()` — потоки доставки, переходов между режимами и отправки событий.
- `Emergency.is_active()` — включён ли режим аварийной поддержки. Меняется сразу, ещё до рассылки команд.
- `Emergency.on_check(result)` — реакция на результат проверки (`on_result`): нарушение включает режим, успех в штатном режиме разрешает трафик. Из аварийного режима выводит только восстановление.
- `Emergency.enter(violations)` — вход в режим (FR-48). Не блокирует вызывающий поток; повторный вызов ничего не меняет.
- `Emergency.leave()` — выход из режима после успешной повторной проверки. Повторный вызов ничего не меняет.
- `Emergency.allow_traffic()` — `traffic.unblock` после успешной проверки (FR-04).
- `Emergency.log_event(...)` — постановка `log.write.event` в очередь на отправку в ПС-2 (поля таблицы `events`, с. 41). `result` — 1 или 0: так принимает ПС-2 (`event_log.write_event`, ветка `logd/stubs`).

#### `restore.py`
- `RestoreError` — копия не совпала с эталоном или восстановление не выполнено.
- **Константы:** `RESTORE_CMD` (`sudo -n /usr/lib/fw/bin/fw-restore`, путь из шаблона `etc/sudoers.d/fw`).
- `backup_path(backup_dir, path)` — путь резервной копии.
- `verify_backup(backup_dir, path, baseline)` — сверка резервной копии с эталоном.
- `restore_file(backup_dir, path, baseline)` — восстановление файла через sudo; копия с несовпадающей суммой не используется (FR-49). Подложенный файл без записи в эталоне не удаляется.
- `update_backup(backup_dir, path)` — обновление резервной копии после штатного изменения (FR-50): зеркало путей как в `mkbaseline`, замена через временный файл.

#### `mkbaseline.py`
- **Константы:** `KEY_BYTES = 32` (длина ключа HMAC; в спецификации не задана).
- `staged(root, path)` — путь файла внутри каталога сборки.
- `build(root, config)` — для каждого пути из `integrityd.files` хэширует файл из каталога сборки, кладёт копию в `backup_dir` с зеркалированием путей (`/etc/fw/config.json` → `backup/etc/fw/config.json`) и пишет `baseline.json` под HMAC. Файлы `SAVED_FILES` могут отсутствовать: записи и копии для них появятся при первом `config save`; любой другой отсутствующий файл — ошибка сборки. Ключ создаётся (0400), если его ещё нет в каталоге сборки. Владельца `fw-integrityd` назначает установщик пакета.
- `main(argv)` — запуск из командной строки.

#### `__main__.py`
- **Константы:** `SOCK_PATH`, `CONFIG_PATH = /etc/fw/config.json` (допущение: имя файла в спецификации не задано), `DEFAULT_CONFIG_PATH = /etc/fw/default/config.json` (допущение: на с. 30 задан только каталог), `COMMANDS`, `ALLOWED_SRC` (источники команд, с. 36), `CHECK_PERIOD_MIN_SEC = 10`, `CHECK_PERIOD_MAX_SEC = 3600` (с. 8), `MAX_CONTROLLED_FILES = 64` (с. 29).
- `load_config(path)` — чтение раздела `integrityd` конфигурации (`integrityd_config_t`, с. 39) с проверкой: абсолютные пути, `check_period_sec` 10–3600, не более 64 файлов. Если `CONFIG_PATH` не существует, читается `DEFAULT_CONFIG_PATH` (первый запуск, FR-04); другой путь значениями по умолчанию не заменяется.
- `handle(msg, checker, em)` — обработка запроса для `fwcommon.protocol.serve` (раздел 3).
- `format_table(result, baseline_path)` — таблица «файл / статус».
- `run_check(config_path)` — разовая проверка для `python -m fw_integrityd check`.
- `run_daemon(config_path)` — работа службы (раздел 4).
- `main(argv)` — запуск подсистемы или подкоманды `check`.

## 3. Команды протокола (JSON по Unix-сокету)

Все сообщения передаются в конвертах по стандарту `common/PROTOCOL.md`. Форматы `payload` команд ПС-6 в спецификации не описаны: поля ниже согласованы с заглушкой ПС-6 стенда CLI (`tests/stand/mock_core.py`, ветка `cli/stand`) или добавлены нами.

### Принимает (с. 36)

| Команда | Назначение | Источник |
|---|---|---|
| `integrity.check` | принудительная проверка | ПС-3, ПС-4 |
| `integrity.status` | результат последней проверки и текущий режим (штатный / аварийный) | ПС-3, ПС-4 |
| `integrity.restore` | восстановить файл из резервной копии | ПС-3, ПС-4 |
| `integrity.update_baseline` | обновить эталон после штатного изменения | ПС-3, ПС-4 (при `config save`); ПС-5 (при `user add`, `user edit`, `user delete`) |

`integrity.update_baseline` принимает пустой `payload` — так её вызывает ПС-5 (`authd/fw_authd/__main__.py`, `notify_integrity`). Какие файлы обновить, ПС-6 определяет по `src`.

`integrity.status` — основной способ для ПС-3 и ПС-4 узнать режим: они запрашивают его при старте, входе и перед каждой командой, ПС-4 — при каждом web-запросе (с. 34, 35). Команда только читает последний результат: не запускает проверку, не ждёт идущую и не регистрирует событий. Значения `mode` — `normal` и `emergency`: ПС-3 считает МЭ аварийным при любом значении, кроме `normal` (`cli/fw_cli/core.py`, ветка `cli/stand`).

Ответы команд:

| Команда | `status` | `payload` | Ошибки |
|---|---|---|---|
| `integrity.status` | `ok` | результат проверки и `mode` | — |
| `integrity.check` | `ok`, в том числе при нарушении: проверка выполнена | результат проверки и `mode` | — |
| `integrity.restore` с `{"file": путь\|"all"}` | `ok`, если повторная проверка прошла | результат проверки, `mode`, `errors` | `M08` — нарушение осталось; `M06` — файл не из `integrityd.files` |
| `integrity.update_baseline` | `ok` | пустой | `M10` — аварийный режим; без кода — сбой обновления |

Команда неизвестна или источник не из таблицы — `M14`. Обе `integrity check` и `integrity restore` доступны в аварийном режиме; `integrity.update_baseline` отклоняется с `M10` (FR-49).

Команды CLI (с. 26): `integrity status` (RO, —), `integrity check` (RW, `E42` / `E50` / `E43`), `integrity restore ФАЙЛ|all` (RW, `E41` / `E50` / `E43`) — все доступны в режиме аварийной поддержки, в web — раздел «Система».

### Отправляет (с. 36)

- `traffic.block`, `traffic.unblock`, `state.clear` → ПС-1.
- `emergency.enter`, `emergency.exit` → ПС-3 **и** ПС-4 (для смены приглашения и запрета команд).
- `log.write.event` (`E40`, `E41`, `E42`) → ПС-2.
- `log.flush` → ПС-2: ПС-6 указана источником в таблице «Входящие команды ПС-2» (с. 34), но не перечислена в «Отправляет» ПС-6 (с. 36). Не реализовано.

### Уведомление ПС-3 и ПС-4 о режиме

- Аварийный режим общесистемный: `emergency.enter` и `emergency.exit` уходят в обе подсистемы всегда, независимо от того, в каком интерфейсе открыт сеанс администратора. ПС-6 о сеансах не знает.
- Сообщения отправляются как запросы с ответом (`type=request`), а не как события. У каждого получателя свой поток, поэтому недоступность одного не задерживает другого.
- При отсутствии ответа: до двух повторов с тем же `msg_id` (`protocol.request`), затем неуспешный результат в журнале (FR-28) и повтор отправки каждые `DELIVERY_RETRY_SEC`, пока получатель не подтвердит режим. Ответ `status=error` режим не подтверждает.
- Команды идемпотентны, поэтому повторная отправка безопасна. Если режим сменился до подтверждения, получатель получит только последнюю команду.
- `emergency.enter` несёт `{"error_code": "M08", "error_message": ...}`: своего вывода для администратора у ПС-6 нет.

Порядок при нарушении целостности:

1. `traffic.block` и `state.clear` → ПС-1;
2. `emergency.enter` → ПС-3 и ПС-4;
3. `E40`;
4. `M08` (также в stderr службы).

Порядок при успешном восстановлении:

1. повторная проверка;
2. `traffic.unblock` → ПС-1;
3. `emergency.exit` → ПС-3 и ПС-4;
4. `E41`.

`E40` и `E41` регистрируются один раз, после первой попытки у всех получателей. Если кто-то не ответил, событие получает `result = 0`, `error_code = M16` и `details.failed` — получателей с причиной, а доставка продолжается. Команды к ПС-1 повторяются так же: без `traffic.block` трафик продолжал бы идти, а на первый `traffic.unblock` ПС-1 ещё может не отвечать (раздел 4).

## 4. Регистрируемые события и сообщения

| Код | Описание |
|---|---|
| **E40** | Нарушение целостности контролируемых файлов |
| **E41** | Восстановление целостности, возобновление обработки трафика |
| **E42** | Проверка целостности по запросу администратора (результат) |
| **M08** | Ошибка: нарушена целостность файлов. Трафик заблокирован. Режим аварийной поддержки |
| **M10** | Ошибка: недопустимая операция в режиме аварийной поддержки |

## 5. Хранимые данные (с. 29–30)

| Путь | Содержимое | Владелец, права |
|---|---|---|
| `/etc/fw/hmac.key` | Ключ HMAC файла эталонов | `fw-integrityd`, 0400 |
| `/var/lib/fw/baseline.json` | Эталонные хэши SHA-256 контролируемых файлов | `fw-integrityd`, 0600, защищён HMAC |
| `/var/lib/fw/backup/` | Резервные копии контролируемых файлов | `fw-integrityd`, 0700 |

ПС-6 читает контролируемые файлы через ACL (`setfacl`), записывает их только при восстановлении через sudo.

`save_baseline` создаёт временный файл рядом с эталоном, поэтому `fw-integrityd` нужны права на запись в `/var/lib/fw/`. Права самого каталога на с. 30 не заданы.

### Контролируемые файлы (с. 29–30)

Список путей задаётся в `integrityd.files` (с. 29, с. 39), не более `MAX_CONTROLLED_FILES = 64`. В `etc/default/config.json` он пока пуст, и `mkbaseline` на нём завершается ошибкой.

- Перечисляются конкретные файлы: каталоги и маски из таблицы на с. 29–30 не раскрываются.
- Обязательно нужно включить `/etc/fw/config.json`, `/etc/fw/policy.json`, `/etc/fw/accounts.json`, а также файлы `/etc/fw/default/`: без них значения по умолчанию не проверяются.
- Не контролируются `hmac.key` (с. 30) и `baseline.json`: у него своя защита HMAC, резервная копия для него в спецификации не предусмотрена.

## 6. Запуск и тестирование

### Порядок запуска

`fw-integrityd` стартует до `fw-filter` (`Before=fw-filter.service` в юните). ПС-1 стартует в режиме `emergency_mode=1` (drop-all); обработка трафика включается только после успешной проверки командой `traffic.unblock` (FR-04, FR-48, с. 22).

1. Читается конфигурация. Если не удалось — код 2, ПС-1 остаётся в режиме drop-all.
2. Выполняется проверка. Успех — `traffic.unblock`, нарушение — вход в аварийный режим.
3. Запускается сервер на сокете: до этого ПС-3 и ПС-4 получают `M16` и считают режим аварийным (с. 34).
4. Запускается таймер.

ПС-1 поднимается позже ПС-6, поэтому `traffic.unblock` повторяется до подтверждения. Событие при этом не регистрируется: отказ на этом шаге штатный. После каждой успешной проверки в штатном режиме команда отправляется снова: ПС-1, перезапущенная командой `subsystem restart`, снова стартует в режиме drop-all.

### Запуск службы
```bash
# Прямой запуск модуля в Debian 12:
PYTHONPATH=common:integrityd python3 -m fw_integrityd

# Через systemd:
sudo systemctl start fw-integrityd.service
```

### Разовая проверка
```bash
# От fw-integrityd (нужен доступ к ключу и эталону). Код возврата: 0 — всё совпало, 1 — нарушение, 2 — ошибка конфигурации.
sudo -u fw-integrityd python3 -m fw_integrityd check [--config /etc/fw/config.json]
```
Проверка только печатает таблицу «файл / статус»: в аварийный режим она не переводит и событий не отправляет. Статус `not_saved` не считается нарушением, код возврата при нём 0. Подкоманды нет в спецификации: это служебное средство, команду CLI `integrity check` она не заменяет.

### Формирование эталонов при сборке пакета (FR-50)
```bash
# STAGING — корень ФС будущего пакета (файлы ПО МЭ по путям устройства);
# пути файлов, эталона, копий и ключа берутся из раздела integrityd конфигурации.
PYTHONPATH=common:integrityd python3 -m fw_integrityd.mkbaseline --root STAGING --config etc/default/config.json
```

### Запуск unit-тестов

Тесты ПС-6 (`tests/unit/integrityd/`):
- `test_smoke.py` — импорт модулей, согласованность `COMMANDS` и `ALLOWED_SRC`.
- `test_hasher.py` — SHA-256, чтение и запись эталона, подмена хэша, HMAC или ключа, повреждённый и отсутствующий эталон.
- `test_mkbaseline.py` — сборка эталона, ключа и копий в каталоге сборки, права 0400/0600/0700, отсутствие файлов `config save`, ошибки.
- `test_checker.py` — статусы `ok`/`mismatch`/`missing`/`not_saved`, нарушение HMAC, отсутствие ключа, `update_baseline`, таймер, `python -m fw_integrityd check`, конфигурация и значения по умолчанию.
- `test_restore.py` — сверка копии с эталоном, замена файла через sudo, обновление резервных копий.
- `test_emergency.py` — порядок команд при входе и выходе, `traffic.unblock` при запуске, очередь событий, настоящие сокеты (`type=request`, тот же `msg_id`). Отдельные сценарии:
  - **недоступность получателя** (`UnavailableTest`): завис один получатель, а второй получает команду сразу; неуспех в журнале с причиной; повтор до подтверждения; недоступны оба; недоступна ПС-1; `status=error`; `exit` заменяет недоставленный `enter`;
  - **повторная отправка** (`ResendTest`, `SocketTest`): повторный вход и выход не дублируют команды и события, повторы идут с тем же `msg_id`.
- `test_main.py` — источники команд, `integrity.status` без запуска проверки, `integrity.check` и `E42`, `integrity.restore`, `M10` для `update_baseline`, порядок запуска службы.

```bash
# Linux (Debian):
PYTHONPATH=common:integrityd python3 -m unittest discover -s tests/unit/integrityd -t tests/unit -v
```

```powershell
# Windows (PowerShell); тесты прав доступа POSIX и Unix-сокетов пропускаются:
$env:PYTHONPATH = "common;integrityd"
python -m unittest discover -s tests/unit/integrityd -t tests/unit -v
```

## 7. Правила

- Шапка каждого файла по шаблону (см. `CONTRIBUTING.md`).
- Данные от администратора и из сети проверяются на входе; данным другой подсистемы без проверки не доверяют.
- Ошибки возвращаются кодом и сообщением из `common/messages.json`; необработанные исключения не завершают процесс.
- Каждый модуль имеет unit-тесты; ПМИ своей подсистемы пишет её команда (`docs/pmi_template.md`).

## 8. Допущения и открытые вопросы

### Спецификация не задаёт, принято в реализации

| Что | Как сделано |
|---|---|
| Совмещение FR-04 и FR-50: при сборке сохранённых файлов нет | `mkbaseline` допускает отсутствие только `SAVED_FILES`, записи появляются при первом `config save` (толкование, тимлиду сообщить) |
| Законно отсутствующий файл | статус `not_saved`; название наше |
| Файлы, которые обновляет `integrity.update_baseline` | определяются по `src`, а не по `payload` |
| Имена `/etc/fw/config.json`, `/etc/fw/default/config.json` | допущение; `cli/fw_cli/core.py` (ветка `cli/stand`) использует тот же путь сохранённой конфигурации |
| Форматы `baseline.json` и результата проверки, длина ключа HMAC | см. раздел 2 |
| Регистрация `E31` при первом запуске (FR-04 не называет подсистему) | ПС-6 не отправляет: на с. 36 её события — `E40`, `E41`, `E42` |
| `integrity restore` для подложенного файла, которого нет в эталоне | файл не удаляется, права sudo не расширяются, команда возвращает `M08`, режим остаётся аварийным |
| Период повтора `emergency.*` и команд ПС-1 | 5 с, как у событий (с. 32) |
| Сколько раз регистрировать неуспех доставки | один раз на переход, в событии `E40`/`E41`: иначе постоянная недоступность заполняла бы журнал |
| Коды событий для неуспеха доставки | `E40` и `E41` с `result = 0`: на с. 36 других событий у ПС-6 нет |
| Доставка `traffic.*` и `state.clear` | повторяется до подтверждения, как `emergency.*`: на с. 36 повторы заданы только для них, но п. «Запуск» на с. 22 без этого не выполняется |
| `traffic.unblock` после каждой успешной проверки в штатном режиме | иначе ПС-1 после перезапуска навсегда осталась бы в режиме drop-all |
| `M08` администратору | поле `payload` команды `emergency.enter` и stderr службы: как ПС-6 выводит сообщение, спецификация не задаёт |
| Код ошибки неудачного восстановления | `M08`: файлы нарушены, трафик заблокирован, режим аварийный. `M01`–`M16` другого подходящего кода не содержат |
| Выход из аварийного режима | только через `integrity restore`, даже если обычная проверка уже прошла (с. 21). Если администратор исправил файл вручную, выход выполняет `integrity restore all` |
| `integrity.update_baseline` при сбое | ответ `status=error` без кода: подходящего кода нет |

### Известные ограничения

- Если `accounts.json` подменён и до следующей проверки выполнена `user add`, `user edit` или `user delete`, подмена войдёт в эталон: ПС-6 не отличает её от штатной записи ПС-5.
- Если копии обновлены, а записать эталон не удалось, копия и эталон разойдутся до следующего штатного обновления.
- Список `integrityd.files` читается из `config.json` до проверки, поэтому изменение списка эта проверка не обнаруживает. Риск принят.

### Открытые вопросы

- Кто слушает `/run/fw/cli.sock` и `/run/fw/web.sock`. Процесс CLI запускается на каждый вход, запросы PHP независимы. Если постоянного получателя нет, ПС-6 бесконечно повторяет отправку: на работу это не влияет, режим клиенты узнают через `integrity.status`.
- Как ПС-3 и ПС-4 узнают, что пора загрузить политику через `rule.replace` после `traffic.unblock` (с. 22): отдельного уведомления в спецификации нет.
- Если повреждены и файл, и его копия, или `baseline.json`, восстановить их через `integrity restore` нельзя. Спецификация не описывает этот случай.
- Перезапуск служб после восстановления: ПС-1 читает политику только при запуске и может продолжать работать с подменённой политикой из памяти.
- Формат `last_check_ts`: сейчас `ГГГГ-ММ-ДД чч:мм:сс`, как в заглушке стенда CLI, а на с. 32 время в сообщениях задано как ISO 8601 с миллисекундами.
- Показ статуса `not_saved` в ПС-3 и ПС-4. Сейчас `integrity restore` для такого файла отвечает `ok`, если нарушений нет, а причина лежит в `errors`.
- Список файлов `config save`: если пишутся другие `/etc/fw/*.json`, их нужно добавить в `UPDATED_FILES`. Сохранённый `config.json` должен содержать раздел `integrityd`, иначе `load_config` вернёт ошибку.
- Источник `log.flush` (см. раздел 3) и поля `log.write.event`: `result` на с. 32 строка, на с. 41 число; принято число.
- Права сокета: с. 31 требует 0660 и группу `fw-mgmt`, `protocol.serve` ставит 0600. Пока это не исправлено в `common/`, ПС-3 и ПС-4 не смогут подключиться к ПС-6.
