## Как устроено выполнение команды

1. `parser.parse(строка)` → `Command`: команда из таблицы, позиционные и именованные аргументы (M14 — нет такой команды, M06 — не те аргументы).
2. `session.check` — `auth.check {session_id, cmd}` в ПС-5 перед каждой командой (кроме logout / exit): право роли решает ПС-5 (M03, событие E50 пишет она же), M15 — сеанс завершён, M16 — ПС-5 не отвечает, команда отклоняется. `auth.check` продлевает сеанс, `auth.ping` не отправляется. Роль в CLI хранится только для приглашения `[rw]` / `[ro]`.
3. `core.access_error(spec, аварийный_режим)`: M10, если команда недоступна в аварийном режиме.
4. `validation.check_command(cmd, интерфейсы, номера_правил)`: значения полей (M06).
5. Подтверждение для команд с `confirm`: только ответ `y` выполняет команду.
6. Выполнение через подсистемы. Правила: ядро держит рабочую копию политики, пишет временный `policy.json` (`validation.rule_to_filter`) и отправляет `rule.replace` с путём к нему. В файл `/etc/fw/policy.json` изменения попадают только по `config save` (FR-41a).

## Входящие команды и режим работы

- `listener.start` занимает `/run/fw/cli.sock` (0600), если его не слушает другой процесс. Процесс CLI запускается на каждый вход, а сокет один, поэтому команды принимает первый запущенный CLI. Остальные проверяют перед каждым приглашением, не освободился ли сокет, и занимают его.
- `emergency.enter` / `emergency.exit` принимаются только от `integrityd`, `session.terminate` — только от `authd`; от других отправителей — M14. Повторные команды состояния не меняют, ответ успешный (`{"mode": "emergency" | "normal"}`).
- Режим (`Core.emergency`): принятое `emergency.enter` действует сразу; иначе — `integrity.status` ПС-6 при старте (`Core.startup_notice`: до запроса идентификатора выводится M08 или M16), после входа и перед каждой командой; ПС-6 не отвечает (M16) — режим аварийный.
- Если команда пришла, пока CLI ждёт ввода, приёмник посылает процессу SIGUSR1: CLI выводит M08 и новое приглашение (`[EMERGENCY]` или `[rw]` / `[ro]`) без нажатия Enter. Во время выполнения команды сигнал игнорируется, изменение показывается перед следующим приглашением.
- `session.terminate {"session_id": "...", "reason": "..."}`: если это сеанс данного процесса, CLI выводит M15 с причиной и завершается; команда, введённая после этого, ядром не выполняется (M15). Сеанс другого процесса этот процесс не трогает: тот получит M15 от ПС-5 при следующем запросе.

## Интерфейсы и маршруты

- `if list` / `if show` — колонка «Управляющий / фильтрующий»; управляющие интерфейсы — `is_mgmt` в `config.json` (`iface_config_t` ТЗ), на стенде — `--mgmt eth0`.
- `if ip ИМЯ адрес/маска` — только для управляющего интерфейса, иначе M06 («только управляющий интерфейс: eth0»).
- `route add сеть/маска шлюз` — шлюз должен лежать в сети управляющего интерфейса, маршрут ставится через него; `route del` — только маршруты через управляющий интерфейс (M06), нет маршрута — M13.
- Изменения регистрируются событием E33; ошибка ОС (`sudo`, `ip`) — M16 с текстом ошибки.

## Запуск

```bash
PYTHONPATH=common python3 tests/stand/mock_core.py /tmp/fw &        # заглушки подсистем
PYTHONPATH=common:cli python3 -m fw_cli --run-dir /tmp/fw --ifaces eth0,eth1,eth2 --mgmt eth0 --net stand
```

На МЭ: `python3 -m fw_cli` (сокеты `/run/fw`, интерфейсы из `/etc/fw/config.json`). Если ПС-6 не отвечает, режим считается аварийным: изменения отклоняются с M10, просмотр и восстановление доступны.

Стенд с настоящими подсистемами других команд — `tests/stand/run_stand.sh --real authd,logd` (см. `tests/stand/README.md`).

Аварийный режим на стенде: `kill -USR1 <pid mock_core>` — нарушение целостности (`emergency.enter`), `kill -USR2 <pid mock_core>` — восстановление (`emergency.exit`).

## Тесты

```bash
make test                                   # все unit-тесты, включая tests/unit/cli
python3 tests/stand/test_stand_codec.py     # заглушки подсистем (tests/stand)
```

`tests/unit/cli/test_shared.py` прогоняет общие сценарии `tests/shared/*.json`: шаги `command` — разбор и проверка ввода, шаги `login` / `notify` / `mode` / `exec` — ядро, приёмник и заглушки (`tests/shared/emergency_mode.json`: аварийный режим, M10, идемпотентность, отправитель, `session.terminate`, M15). ПС-4 прогоняет те же сценарии и должна получать те же коды и поля. `tests/unit/cli/test_listener.py` — входящие команды.
